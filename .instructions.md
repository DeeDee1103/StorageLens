# StorageLens Copilot Instructions

You are an expert assistant for the **StorageLens** project—a .NET 8 microservices SaaS platform for storage analytics and duplicate detection.

## Project Overview

StorageLens is a distributed system that scans file storage (local/NAS), detects duplicates, and provides analytics through a web dashboard. It uses:
- **Runtime**: .NET 8 (C# 12)
- **UI**: ASP.NET Core Razor Pages + Bootstrap 5
- **Messaging**: RabbitMQ
- **Data**: SQL Server with polyglot schema ownership
- **Containerization**: Docker + Docker Compose

## Services

| Service | Port | Responsibility |
|---------|------|-----------------|
| `StorageLens.Web` | 5001 | Razor Pages frontend, UI orchestration |
| `Locations` | 5101 | Storage location metadata |
| `ScanJobs` | 5102 | Scan job lifecycle and progress |
| `FileInventory` | 5103 | File metadata storage and queries |
| `Duplicates` | 5104 | Duplicate group computation |
| `Analytics` | 5105 | Dashboard and reporting data |
| `Scanner` | 5106 | File system traversal and enumeration |
| `Hashing` | 5107 | SHA-256 computation pipeline |
| `Orchestrator` | 5108 | Workflow coordination and retry logic |

## Core Principles

### 1. Service Boundaries & Data Ownership
- Each service owns its own SQL Server database schema
- Cross-service access is **HTTP API only** (no direct DB access)
- Service contracts are defined in `StorageLens.Shared.Contracts`
- Database contexts live in their respective service projects

### 2. Workflow Architecture
- **Synchronous HTTP calls** between services
- **Correlation IDs** propagated across scan workflow stages
- **Health probes** via `/health` endpoints
- **Retry/resume hooks** in the Orchestrator service

### 3. API Design
- REST APIs over HTTP with JSON
- Immutable DTOs in Shared.Contracts
- Backward-compatible contract evolution
- Typed `HttpClient` integrations in consumers

## Development Guidelines

### Before You Code

1. **Understand service ownership**: Which service should own this data/logic?
2. **Check contracts**: Review `StorageLens.Shared.Contracts` for existing types
3. **Respect boundaries**: Never write cross-service queries or direct DB access
4. **Plan tests**: Unit tests required for all service logic

### Coding Standards

- Follow **idiomatic C# and .NET 8** patterns
- Use **meaningful names** and avoid abbreviations
- Keep files **focused and cohesive** (single responsibility)
- Use **immutable DTOs** for API contracts
- **Log with correlation IDs** for cross-service tracing

### Error Handling

- Use **explicit status and progress semantics** in APIs
- Log **actionable context** including correlation IDs
- Distinguish **recoverable vs. terminal** workflow failures
- Avoid silent failures or generic error messages

### Documentation Requirements

**CRITICAL**: Any change to services, contracts, workflows, or deployment must update corresponding `docs/` files in the same PR.

- `docs/technical/` for API and schema changes
- `docs/architecture/` for interaction/workflow changes
- `docs/operations/` for deployment/scaling changes
- `docs/CHANGELOG.md` for all user-visible changes

### Testing

- Write **unit tests** for all service logic
- Test **cross-service contracts** in integration tests
- Mock external HTTP calls in unit tests
- CI enforces successful builds and passing tests before merge

## Common Tasks

### Adding a New Service
1. Create project under `src/ServiceName/`
2. Add DbContext and schema to `infra/main.bicep` and SQL initialization
3. Define contracts in `StorageLens.Shared.Contracts`
4. Add health endpoint `/health`
5. Register in `docker-compose.yml` with service port
6. Document in `docs/architecture/microservices-architecture.md`
7. Update `docs/CHANGELOG.md`

### Adding API Endpoints
1. Create controller with HTTP methods
2. Define immutable DTOs in `StorageLens.Shared.Contracts`
3. Add unit tests in `tests/ServiceName.Tests/`
4. Update API documentation in `docs/technical/api-specification.md`
5. Document breaking changes in `docs/CHANGELOG.md`

### Cross-Service Communication
1. Register typed `HttpClient` in consuming service DI container
2. Define contracts in `StorageLens.Shared.Contracts`
3. Implement error handling and retry logic
4. Propagate correlation IDs in request headers
5. Add integration tests covering the interaction

### Database Schema Changes
1. Update DbContext in the owning service
2. Update `infra/main.bicep` for deployment
3. Add migration script if manual steps needed
4. Document in `docs/technical/database-schema.md`
5. Update `docs/CHANGELOG.md` with migration notes

## Build & Run

```bash
# Build all services
dotnet build StorageLens.sln

# Run tests
dotnet test tests/

# Local development (watch mode)
dotnet watch run --project src/StorageLens.Web/StorageLens.Web.csproj

# Docker Compose (all services)
docker-compose up

# Run specific service tests
dotnet test tests/StorageLens.Services.Orchestrator.Tests/
```

## Code Review Focus

When reviewing PRs, ensure:
- ✓ Each service respects its bounded context
- ✓ No direct cross-service database access
- ✓ Contracts are immutable and versioned
- ✓ Error handling is explicit and logged
- ✓ Tests pass and coverage is adequate
- ✓ Documentation is updated in `docs/`
- ✓ `docs/CHANGELOG.md` reflects the changes
